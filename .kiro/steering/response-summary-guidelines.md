# 响应总结生成指南

## 核心原则

**不要每次都生成冗长的总结**。只在真正有必要时才生成总结。

## 何时生成总结

### ✅ 应该生成总结的情况

1. **完成了复杂的多步骤任务**
   - 修复了多个相关的 bug
   - 重构了多个文件
   - 实现了完整的功能模块

2. **用户明确要求总结**
   - 用户说"总结一下"
   - 用户问"做了什么修改"
   - 用户需要了解整体变更

3. **创建了重要的文档或配置**
   - 生成了架构设计文档
   - 创建了配置文件
   - 编写了使用指南

4. **解决了关键问题**
   - 修复了严重的 bug
   - 解决了性能问题
   - 处理了安全漏洞

### ❌ 不应该生成总结的情况

1. **简单的单一操作**
   - 修改了一个文件
   - 添加了一个函数
   - 修复了一个小 bug

2. **回答问题或提供信息**
   - 解释代码逻辑
   - 回答技术问题
   - 提供建议

3. **中间步骤**
   - 正在进行多步骤任务的中间环节
   - 等待用户反馈
   - 需要继续操作

4. **用户只是查看或询问**
   - 查看文件内容
   - 询问如何实现
   - 探索代码结构

## 总结的格式

### 简洁总结（推荐）

对于大多数情况，使用 1-3 句话的简洁总结：

```
✅ 修复完成。优化了 rename 方法，使用复制+删除策略处理目录，解决了 Windows EPERM 错误。
```

### 详细总结（仅在必要时）

只有在以下情况才使用详细总结：
- 修改了 5 个以上的文件
- 实现了完整的功能模块
- 用户明确要求详细说明

详细总结应包含：
- 问题描述（1-2 句）
- 修复方案（3-5 个要点）
- 修改的文件列表
- 测试建议（可选）

## 具体示例

### ❌ 不好的做法（过度总结）

```
## 修复总结

我已经成功修复了文件预览问题。

### 问题描述
1. 新建文件夹内的文件无法预览
2. 从回收站恢复的文件无法预览
3. Windows 系统出现 EPERM 错误

### 修复内容
- 修改了 main.ts 文件
- 修改了 file.service.ts 文件
- 修改了 local-storage.adapter.ts 文件
- 添加了兜底逻辑
- 优化了 rename 方法
- 新增了 copyDirectory 方法

### 测试建议
1. 测试新建文件夹上传
2. 测试删除和恢复
3. 测试 Windows 系统
...（省略 20 行）
```

### ✅ 好的做法（简洁明了）

```
✅ 修复完成。优化了 rename 方法，使用复制+删除策略处理目录，解决了 Windows EPERM 错误。
```

或者（如果是复杂任务）：

```
✅ 文件预览问题已修复：
1. 添加了静态文件服务的兜底逻辑
2. 修复了删除/恢复时的路径同步问题
3. 优化了 Windows 系统的目录移动策略

请测试新建文件夹上传和回收站恢复功能。
```

## 响应风格

### 推荐的结束方式

**简单任务**：
- "完成。"
- "已修复。"
- "✅ 已更新。"

**中等任务**：
- "✅ 修复完成。[1 句话说明]"
- "已完成 [具体内容]。"

**复杂任务**：
- 使用 3-5 个要点的列表
- 包含关键修改和测试建议
- 不超过 10 行

### 避免的模式

❌ 不要使用：
- "## 修复总结"（除非真的很复杂）
- "## 问题描述"（用户已经知道问题）
- "## 修改的文件"（除非修改了很多文件）
- "## 注意事项"（除非有重要警告）
- "## 后续优化建议"（除非用户要求）
- 重复用户已经知道的信息
- 冗长的项目符号列表

## 特殊情况

### 创建文档时

如果创建了独立的文档文件（如 README.md、修复说明等），在响应中只需简单提及：

```
✅ 已创建修复说明文档 FILE_PREVIEW_FIX.md，包含详细的问题分析和解决方案。
```

不需要在响应中再次重复文档内容。

### 用户追问时

如果用户对之前的操作有疑问或需要更多信息，再提供详细说明。不要预先假设用户需要所有细节。

## 记住

- **简洁是美德**
- **用户的时间很宝贵**
- **只说必要的内容**
- **让代码和文档说话**
- **避免重复和冗余**
